# 我做了一个 skill：debug-simple —— 小问题快速修，但要会升级

> **推文草稿（Twitter/X）**
> 不是每个 bug 都该开复杂评审，但“简单”不能只看改几行。`debug-simple` 先确认根因局部、修复唯一、风险可控；任一不满足就升级到 `debug-hard` 🧩
> `npx skills add hifizz/skills --skill debug-simple`
> 背后的判断标准 👉 https://zilin.im

## 这是什么（技能本身）

`debug-simple` 用于范围明确、低风险且修复路径唯一的缺陷，例如局部条件写反、孤立回归、文案/参数错误，或能够直接沿用既有模式的修复。

它先用一句话复述问题，接着只读确认根因，再简短说明改动与验证方式，随后直接实施。用户的“修复”请求可作为实施授权，但前提是问题确实满足低风险条件。

```bash
npx skills add hifizz/skills --skill debug-simple
```

## 为什么做它（原因 / 过程）

如果所有调试都走长流程，小问题会被不必要的确认成本拖慢；如果所有调试都直接开改，复杂问题又会演变成局部补丁和架构漂移。

因此它不把“简单”定义为改动文件少，而是定义为一组条件：预期行为明确、根因单一局部、修复路径唯一、无需用户做产品选择，并且不改接口、数据模型、依赖、权限或架构。

这组条件也是它与 `debug-hard` 的分界线。任何一项不成立，agent 必须说明原因并升级，而不是为了维持“快速”标签继续猜。

## 什么时候用它（适用场景）

- 某个明确条件写反，已能定位到唯一代码分支。
- 已有同类实现，修复只是把局部行为恢复为既定模式。
- 已知回归的预期行为和验证方式，不涉及产品或架构决策。

不要用于范围不清、需要比较方案、涉及跨层行为或用户要求先确认方案的问题；这些应直接使用 `debug-hard`。
