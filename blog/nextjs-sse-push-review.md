# 系统设计自评：这套 SSE 推送系统做得怎么样？有没有更好的方案？

> 这是 [nextjs-sse-push](../skills/nextjs-sse-push) 系列的第三篇。[第一篇](./nextjs-sse-push.md)介绍 skill 本身，[第二篇](./nextjs-sse-push-design.md)复盘设计与实现。这一篇换一个立场：**如果我是评审，我会怎么批这套设计？** 写自己系统的缺点比写优点难得多，但这部分往往才是对读者最有用的。

---

## 总评

**架构方向正确、工程细节成熟，但可靠性语义有一个真实的洞，presence TTL 有一个接近 bug 的参数设计。**

放在它的甜点区里——自托管常驻进程（Fly.io / Docker）、通知类可丢消息、技术栈里已有 Redis——这是一个 8 分方案。离开这个甜点区，短板会很快暴露。下面分开说。

## 做得对的地方

**1. 推送与连接解耦是教科书式的。** `pushToUser` 只 publish 不摸连接池，让"任意进程可推"和"多实例扩展"两个问题被同一个决策一次解决。这是整个设计里最值钱的一步，也是很多第一版实现（直接在内存连接池上做单例广播）绕不过去的坎。

**2. Worker 独立进程 + jobId 幂等。** 延迟任务不被 Web 部署重启杀掉；"用户刷新 10 次只调度 1 次"靠确定性 jobId 在队列层解决，而不是靠业务代码小心翼翼。这两件事在业务上是刚需，而且第一版几乎没有人做对。

**3. 踩坑密度高。** 心跳的双重用途（保活 + 客户端死连接检测）、EventSource 自定义事件静默丢消息、三种 Redis 连接严格分离、Next.js 热重载的 globalThis 单例——这些细节不是设计出来的，是被真实流量打出来的。一套系统的成熟度恰恰体现在这类"没人会写进教程"的地方。

## 真实的短板

### 1. 可靠性语义是 at-most-once，离线队列基本是摆设

Redis Pub/Sub 是 fire-and-forget：实例重启、Redis 订阅断连的窗口期，消息直接蒸发，没有任何补偿。

更要命的是**实例内存离线队列在多实例下几乎无效**：队列绑定在单实例内存里，用户断线重连时经过负载均衡，大概率落到**另一个**实例——原实例队列里的消息永远送不出去。追溯原项目源码时还发现，`addToOfflineQueue` 定义了但在 `sendMessage` 的离线路径里根本没被调用，说明这个机制从一开始就是个半成品。

对"AI 主动发消息"这种业务，正确的做法其实是**消息落库为唯一真源**，SSE 只当"有新消息"的信号用：前端连上先拉历史、再听增量。这一点在设计文章的"边界"一节里被轻描淡写地列为"演进方向"，严格说它应该是**默认设计**。

### 2. presence TTL = 7200s 是接近 bug 的参数

心跳每 30 秒就 `EXPIRE` 续期一次 presence key，所以 7200 秒的长 TTL **完全没有省下任何 Redis 写入**；而它的代价是实打实的：实例 crash（走不到优雅的 unregister）后，用户会**假在线最长 2 小时**。这 2 小时内，Worker 查 presence 认为用户在线、跳过离线推送兜底，消息就丢了。

正确的值应该是心跳间隔的 2~3 倍（比如 90 秒）：心跳还活着就续期，实例死了 90 秒内自动出清。这是我评审任何系统时都会揪的那类问题——**参数的量级和它的机制对不上**。坦白说，抽 skill 模板时我原样继承了这个默认值，这一条同样适用于批评我自己。

### 3. 广播扇出浪费了 presence 里已有的信息

presence 的 Redis Set 成员就是 workerId——系统**明明知道**用户连在哪个实例，却让所有实例反序列化所有消息，无关实例还要各自查一次 presence 才能决定"不处理"。

发布时先读 presence，按 workerId 定向发到 `sse:push:{workerId}` 频道，扇出成本就从 O(实例数) 降到 O(1)。现在的设计把一份已经花钱维护的路由信息只用来做在线/离线布尔判断，是明显的浪费。

### 4. 离线兜底的去重被推给了业务

用户全局离线时，**每个**无连接实例都会触发 `onOfflineMessage`，全局只发一次 Push Notification 的语义要业务自己拿分布式锁收口。这是把架构层没解决的竞态转嫁给了每一个使用方——每个接入离线推送的人都要重新想一遍锁的问题。更好的归宿是把"全局离线判断 + 兜底"收敛到单点（见下文 Streams 方案，consumer group 天然解决）。

### 5. 一些小的低效

- **每连接一个心跳 `setInterval`**：几千个并发连接就是几千个 timer。应该每实例一个全局 tick，遍历连接池批量写心跳。
- **前端 401 和网络错误走同一条重连路径**：未登录用户会无意义地重连 10 次。EventSource 的 `onerror` 拿不到 status code，这个锅一半是协议的——但至少可以在建连前先 fetch 探测一次鉴权状态。

## 更好的方案

### 同等约束下的改进版（自托管，保留 SSE + Redis）

这是我认为这套系统的"正确终态"，四个改动全部向后兼容：

1. **Redis Streams 替代 Pub/Sub + 消息落库**：`XADD` 到分片 stream，投递有确认；前端重连带 `Last-Event-ID`，服务端从库里补拉断线期间的消息 → at-least-once，实例内存离线队列直接删除。
2. **定向路由**：发布时读 presence 的 workerId，发 per-worker 频道。
3. **兜底收口**：用 stream consumer group 起一个全局的离线兜底 consumer，竞态和去重在架构层消失，`onOfflineMessage` 的分布式锁要求随之取消。
4. **参数修正**：presence TTL 降到 90s；心跳改全局 tick。

### 换组件，按场景分

| 场景 | 方案 | 理由 |
| --- | --- | --- |
| 不差钱 / 不要求数据主权 | 托管 realtime（Ably / Pusher / Supabase Realtime） | 这类系统的真实成本不在首次搭建，而在长尾运维（假在线、代理缓冲、重连风暴）。托管服务把长尾全吃掉。自建的合理性来自"Redis 已在栈里 + 想零外部依赖"，前提不成立时，**买比造好** |
| Cloudflare 生态 | Durable Objects / PartyKit | 每用户一个 DO，路由、presence、连接休眠是**平台原语**——上面短板 1、2、3 在架构层就不存在。对新项目这是最优雅的替代 |
| 规模很小、已有 Postgres | `LISTEN/NOTIFY` | 连 Redis 都省了。注意 8KB payload 上限和连接数限制 |
| 必须部署 Vercel | SWR 轮询或托管服务 | Serverless 函数时长上限会周期性掐断 SSE，这套系统在 serverless 上是逆势而为，别硬上 |

### 什么时候现在这套就是对的

自托管常驻进程、纯单向推送、消息可丢（通知/角标/信号类）、已有 Redis、不想引入外部 SaaS——五个条件都满足时，这套系统是依赖最少、心智负担最小的选择。原项目恰好全部满足，所以它在原项目里是个好设计。

## 结论

如果重来一次，我会改两件事的优先级：**"消息落库 + Streams" 从演进项提为默认设计**，**presence TTL 按机制定量级**。其余的（定向路由、全局 tick、兜底收口）是锦上添花，可以等规模逼出来再做。

这也是写自评的价值所在：一套系统"好不好"从来不是绝对的，而是**它的假设和你的场景匹不匹配**。把假设写清楚、把短板说透，比展示一张漂亮的架构图更能帮下一个使用者做决定。
