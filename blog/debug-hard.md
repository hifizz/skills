# 我做了一个 skill：debug-hard —— 复杂调试先确认，再修改

> **推文草稿（Twitter/X）**
> 复杂 bug 最浪费时间的不是改不出来，而是还没确认问题和方案就开始改：局部补丁、擅自换架构、来回返工。把这套约束沉淀成 `debug-hard` 了 🧩

## 这是什么（技能本身）

`debug-hard` 是复杂调试的四阶段工作流：**确认问题 → 诊断问题 → 确认方案 → 具体实现**。

它适用于根因、范围或修复路线尚不明确的 bug，尤其是涉及既有架构约束、参考实现、多种可行方案，或用户明确要求先诊断再修改的任务。

诊断阶段只允许读代码、搜索和无写入验证；方案未经确认前不改文件。方案必须说明根因证据、要保留的机制、最小修改、影响范围和验证方式。实现中出现新的关键选择，就回到方案确认，而不是顺手扩大改动。

```bash
npx skills add hifizz/skills --skill debug-hard
```

## 为什么做它（原因 / 过程）

真实调试里最常见的返工不是技术能力不够，而是流程把“诊断”“设计决策”“实施授权”混成了一步。看见一个症状就先打一针局部补丁，用户质疑后又直接抛出另一套架构；两边都没有先确认约束，结果越改越偏。

这个 skill 把几个容易被省略的边界写死：参考实现是证据，不是迁移授权；用户的“为什么”和“不满意”是重新诊断的输入，不是继续改代码的许可；用户已经明确的方案才可直接进入实施。

它不是为了制造仪式感。问题清楚时，“确认问题”和“诊断”可以连续完成；但涉及产品选择、架构取舍或未知范围时，必须停下来要信息，避免 agent 用猜测替代决策。

## 什么时候用它（适用场景）

- 复现点明确，但不知道根因，或有多个合理修复路线。
- 用户给了参考项目，却没有授权迁移其整体设计。
- 变更可能触及 API、数据模型、权限、架构或跨层行为。
- 用户要求“先查原因”“先给方案”“不要直接改”。

一句话：**当修复本身包含决策时，用 `debug-hard` 把决策和编码分开。**
